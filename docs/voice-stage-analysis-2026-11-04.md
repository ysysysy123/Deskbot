# TTS 阶段与 LLM 首文字实测

日期：2026-11-04。固定合成文本、独立进程；未访问真实聊天历史、启停现有服务或更改运行配置。

## TTS：首个服务端音频是主要等待

[完整结果](tts-stage-benchmark-2026-11-04.json)来自 `benchmark_tts_stages.py`。每模式预热 1 次后测量 30 次，模式顺序交替，均成功。使用同一固定中文文本和 `zh-CN-XiaoxiaoNeural`；每轮输出 312192 字节 PCM，时长 6.504 秒。消费端不按播放节奏等待。

| 指标（ms） | 默认 P50 / P95 | 输入 blocksize=1024 P50 / P95 |
| --- | ---: | ---: |
| 首个压缩音频到达 | 2296.8 / 2734.9 | 2347.0 / 2866.1 |
| 创建 FFmpeg 子进程返回 | 1.0 / 1.1 | 1.0 / 1.2 |
| 首 PCM | 2330.5 / 2784.2 | 2351.5 / 2869.0 |
| 首媒体到首 PCM（逐轮相减） | 3.0 / 85.5 | 3.8 / 7.1 |
| 接收与转码全部结束 | 2958.7 / 3563.6 | 3071.5 / 3583.9 |

首媒体到达前包含连接、请求及服务生成等待；本次计时不能进一步区分这三项。各指标分别计算分位数，不能用分位数直接相减代替逐轮阶段耗时。

缩小输入读取块降低了本轮媒体到 PCM 的尾部等待，但首 PCM P50 慢约 21 ms，P95 慢约 85 ms；没有达到计划中首音频中位数降低 20% 的目标。保留默认转码参数，本次不将这个候选作为性能优化发布。

下一步应针对首媒体之前的连接／服务等待或其他 TTS Provider 做对照。现有转码中位数仅约 3 ms，继续调整本地 PCM 块大小对秒级等待的收益空间有限。

## LLM：当前场景没有观察到重试

[完整结果](llm-first-text-benchmark-2026-11-04.json)来自 `benchmark_llm_first_text.py`。固定合成问题、空历史、无工具，`glm-4-flash`，当前配置允许 1 次重试。预热 1 次后测 30 次，30 次均成功。

| 指标 | P50 | P95 |
| --- | ---: | ---: |
| 首文字 | 667.0 ms | 1976.5 ms |
| 完整文字 | 1120.6 ms | 2726.1 ms |
| 观测到的 SDK 重试事件数 | 0 | 0 |

重试计数读取当前 SDK 的明确重试日志事件，仅保存计数，不保存 URL、认证信息或响应正文。本批没有证据支持通过关闭重试解决长尾。此处是固定文本请求，与此前实际 WebSocket 语音回合的提示、上下文及输入路径不同，不能据此宣称生产首文字延迟改善。

## 复现

在 `server/voice` 目录、包含现有在线 Provider 依赖的环境中执行：

```bash
python scripts/benchmark_tts_stages.py --repeat 30 --warmup 1 --json /tmp/tts-stage.json --audio-dir /tmp/tts-stage-audio
python scripts/benchmark_llm_first_text.py --repeat 30 --warmup 1 --json /tmp/llm-first-text.json
```

TTS 每个模式保留一份成功样例供试听。本次样例位于 `/tmp/deskbot-tts-stage-audio-20261104/`，未进行主观音质评分。上述结果不包含设备播放、VAD 端点或实机插话。
