# 语音与记忆功能的具体改进方案

日期：2026-11-01（America/Los_Angeles）。本次基于当前源码和上次的历史延迟统计，使用临时 SQLite 数据库、合成文本及 Fake VAD/Codec 验证行为；没有启动服务、访问云端模型或修改运行配置。以下是实施方案，尚未修改业务代码。

后续第一批实施及验证结果见 [实施记录](voice-memory-implementation-2026-11-01.md)，包含新增代码、在线合成样本检查和仍待完成的验收。

## 1. 语音优先改哪里

历史普通语音样本：ASR 中位数 131 ms，首文字 1.045 秒，首音频 3.950 秒。首文字至首音频差值中位数 2.713 秒，是应优先细分的等待；不能全部归因于 TTS，也不能承诺优化后固定节省多少。

| 优先级 | 当前行为与证据 | 具体改法 | 如何判断有效 |
| --- | --- | --- | --- |
| 第一批 | 首段只在句号、问号等强标点，或到 100 字上限才输出；逗号不触发短段 | 首段采用更短的语义边界：已有 12–24 个汉字且遇到逗号/分号时可输出；后续仍按整句或较长段合成。这是初始试验参数 | 同一批输入比较首句就绪时间、首 PCM、首 Opus，以及语音自然度和 TTS 请求次数 |
| 第一批 | 英文句点一律断句，`23.5` 被切成 `23.` 和 `5` | 保护数字间小数点，先补跨文本 delta 的处理；避免一看到尾部数字后的句点就立即决定断句 | 小数、日期等常用读法不被截断；中文句号和英文句末仍正常输出 |
| 第一批 | 缺少成句和合成细分计时 | 加首句就绪、TTS 请求开始、首 PCM、音频发送量/时长；已有 first_text/first_audio 继续沿用 | 能区分等待文本、云端合成、解码和播放发送；只做阶段事件，不逐 token 记录 |
| 第二批 | 每句重新创建 TTS 请求和 FFmpeg 进程，分得越细请求越多 | 首段短、后续合并；先测首段缩短收益与句间间隙，保留现有提前合成队列 | 首音频更快，后续无明显断续，整体请求数受控 |
| 第二批 | VAD 当前静音窗口 600 ms | 对固定语音样本比较 450/600 ms，不直接全局降低；慢语速和句中停顿是必要样本 | 450 ms 理论只减少约 150 ms；不能以截断用户为代价 |
| 第二批 | 原生 auto/realtime 在尚未检测到讲话前也累计 PCM 和录音上限 | 尚未讲话时只保留约 180–240 ms 的起始环形缓冲；检测到语音后才进入本轮录音计时。浏览器桥已有类似逻辑 | 原生持续静音不耗尽一轮录音时长，实际开始讲话时保留首字 |
| 后续 | 实机播放期间 handle_audio 直接忽略输入；浏览器桥有独立打断 | 实机打断要结合固件上行与回声效果单独验证；不要直接把扬声器回声当成用户插话 | 用户插话能停止旧音频，扬声器播放自身不会频繁触发 |

代码位置：[分段](../server/voice/src/voice_server/audio/sentences.py)、[语音编排](../server/voice/src/voice_server/session.py)、[Edge TTS](../server/voice/src/voice_server/providers/edge_tts.py)、[转码](../server/voice/src/voice_server/audio/transcoder.py)、[浏览器分轮](../server/voice/src/voice_server/local_testing.py)。

首段不建议设置很短的无条件定时切片。没有标点时在词语中间切开，会影响读法，还会增加 TTS 请求。先试短语边界，拿到成句耗时再决定是否值得加时间上限。LLM/工具循环的取流不能因为切段而反复取消重建。

现有流式转码、后句提前合成、PCM 有界队列已经实现，不需要重做。实机每 60 ms 发一个 Opus 包是配合设备播放队列的机制，不能简单去掉节奏发送来缩短 total_ms。也不建议首先换 ASR：即使把历史 ASR 中位数全部消除，也只有约 131 ms 的收益。

## 2. 当前记忆实现的具体问题

### 2.1 原文重复注入：已复现

当前 recall_for_turn 同时读取近期消息和最多 5 条相关消息，相关查询没有排除近期 ID；_make_messages 只排除与当前提问相同的相关文本。

临时库放入“我喜欢喝拿铁咖啡”、助手回复和当前问题后，近期/相关集合都有 3 条，旧偏好在最终模型输入出现 2 次。这浪费上下文，增加旧内容的权重。

改法：先选近期消息，再从历史候选中排除这些消息 ID 和本轮当前消息 ID；不要只按文本去重，不同时间说出同一句话可能确实是两次事件。摘要与原文允许必要的语义重叠，先处理这种确定的重复行。

### 2.2 按时间选历史会漏掉答案：已复现

当前命中任一二字片段后，直接 `ORDER BY id DESC LIMIT 5`。临时库先写入“喜欢的咖啡是拿铁”，再写 6 条“路过咖啡店”，提问“我喜欢的咖啡是什么”时，5 条检索结果全部来自较新的路过记录，准确答案未入选。

改法：在当前每设备最多 5000 条的规模内，先以 LIKE 取得一个有限候选集，按不同查询词覆盖率排序，时间只做次级排序；候选筛选也不能只拿很近的几十条，否则旧答案仍会被挡在排序前。第一版可在 SQLite 中计算命中词数量并排序后取候选，再在 Python 中去重和组装。优先精确词组、显著关键词，减少“什么”等常见问法造成的弱匹配。

每次取 3–5 条，附时间、角色和消息 ID。改进的是词面检索，对完全不同说法的语义匹配仍有限；先用实际问法验证，再决定是否需要 embedding。

### 2.3 长期事实没有独立存储

目前长期内容主要依赖不断改写的一段摘要，默认摘要输出上限为 256 tokens；不能稳定承担所有偏好、身份和约定。原始消息还有每设备 5000 条上限。

改法：事实单独存，摘要承担对话进展。原文暂时继续现有保留策略，事实不会随原文滚动清理而消失。

### 2.4 后台摘要并不等于闲时整理

schedule_summary 在回复后立即创建任务，达到 12 条新增消息就开始调用模型。它不阻塞当轮语音，但可能与紧接着的下一轮共用模型资源。现在也只处理一次一个批次。

改法：使用一次性闲置计时器，初始可设 20 秒。新讲话/文本到来就取消尚未触发的计时，回复结束后重排。持续模式会一直处于 LISTENING，因此不能把“状态必须 IDLE”当作闲置条件；应看是否有实际讲话、识别、模型或播报活动。已经开始的后台模型调用也可能争抢资源，尤其本地模型，必须在性能验证中单独观察。

### 2.5 被打断的回复没有保存已发送部分

当前只在完整回复成功结束后保存 assistant_text；取消路径不保存助手输出。因此用户听到前半段后说“接着刚才说”，近期上下文可能没有那段内容。

改法：记录哪些语音段已发出及回合是否中断，保存“已发送部分”，而非尚未合成/发送的全部模型文本。若中途只发送了半个段，标记该段不完整；设备没有播放确认时，不应称为“已听到”。长期事实仍只从用户明确表达中抽取，不从助手生成的半截回答推断用户偏好。

## 3. 记忆层第一版结构

继续用 SQLite，扩展现有 MemoryProvider/MemoryService，不增加独立 Node 服务或向量库。

新增 `memory_facts` 表，最小字段：

| 字段 | 用途 |
| --- | --- |
| id、device_id | 事实标识及现有隔离范围 |
| fact_key | 同类事实的稳定键，如 `preference.coffee`；更新时尽量复用已有键 |
| content、category | 一句话事实及类别：身份、偏好、约定、待办 |
| importance | 简单的优先级，第一版不做复杂权重衰减 |
| source_message_id、source_excerpt | 用户原文出处；短摘录在旧原文被清理后仍可说明依据 |
| updated_at、status | 更新时间；active / superseded / forgotten |

每个设备同一事实键只有一条 active 记录。不同偏好不能全压成同一键，例如不同饮料或不同联系人的信息要分开。抽取时提供已有事实键，减少模型为同一意思反复新建键；复合事实有更新时拆成需要更新的单项。

事实更新例子：

```text
用户：我喜欢拿铁。
→ preference.coffee = 喜欢拿铁（来源：该条用户消息）

用户：我现在改喝美式了，不喝拿铁了。
→ 旧条目标记 superseded，新条目 active；两者都保留来源。

用户：忘掉我的咖啡偏好。
→ 对应事实 forgotten，当前注入不再包含它。
```

“忘掉”还必须同时让旧摘要/原文检索不能把这项偏好重新注入或再次抽取。第一版应把遗忘作用范围和处理游标一起落实；仅改 facts.status 不足以兑现遗忘。普通对话不默认隐藏或删除历史；全设备清除继续用现有 clear API，并将事实表一起纳入事务。

按 Device-Id 存的是“设备对应使用者”的记忆，尚不是自动识别个人。第一版延续这一前提，不引入声纹。

## 4. 写入和读取流程

### 写入

1. 用户消息即时落原文库，正常开始回答。
2. 回复结束后排一次闲置整理；普通闲聊仍以新增 12 条消息作为批量门槛。
3. 用户明确说“记住……”或纠正已有偏好时，不等待凑齐 12 条，闲置后处理这一小批；存原文和加入待整理，不应在尚未完成事实写入时声称已完成长期保存。
4. 一次后台调用同时生成结构化的 `summary` 和 `fact_updates`，避免摘要和事实分两次模型请求。事实包含来源消息 ID；只接受当前批次里的真实用户消息作为新用户事实来源。
5. 保存摘要、事实变更和处理游标时使用同一事务。有效结果保存后才推进游标；格式解析失败继续保留原文，下一次有实际对话活动时再安排，不开启后台重试轮询。

当前 256-token 摘要预算不足以同时输出多条事实及其结构；需单设整理输出预算，例如从 768 tokens 起试。预算是实现初值，真实输出量和成本必须实测。既有摘要游标可以继续承担“哪些原文已处理”，不另建复杂任务队列；显式纠错/遗忘的范围和重抽取边界仍需保存。

### 读取

在 ASR 后用本地查询一次取得：有效事实、摘要、近期消息、相关旧消息。MemoryContext 增加 facts，_make_messages 统一组装。

推荐初始预算：最近 10 条消息；事实最多 10–20 条、总计约 600–900 字符；相关旧消息 3–5 条且受总字符预算约束。未摘要消息可以临时多取，但总上下文仍受预算限制，避免后台摘要落后时从 10 条无声膨胀到 64 条长消息。字符预算只是第一版近似，拿到模型 usage 后再校准 token 预算。

当前用户陈述优先于旧事实；有效新事实优先于旧摘要。被 superseded/forgotten 的事实不应又经历史检索或摘要重新主导回答。系统规则与事实材料在组装时清楚分开，保持稳定规则在前，变化记忆在后。当前开启 MCP 时会合并 system 段，记忆规则也要在普通 LLM 路径中一致生效。

明确的“记住、修改、忘记”先使用 MemoryService 方法或小型记忆工具接口落实；普通问答仍自动读记忆，不让模型每轮多做一次工具往返。管理 API 同时提供事实查看、修改和撤销，便于验证它究竟记住了什么。

## 5. 分批实施与验收

| 批次 | 修改范围 | 必须验证的结果 |
| --- | --- | --- |
| A：现有问题 | sentences.py、session.py、memory/sqlite.py | 小数不误切；近期原文只注入一次；旧准确答案不会被几条新弱匹配挤掉；增加阶段计时 |
| B：长期事实 | memory/models.py、base.py、sqlite.py、service.py、session.py、admin_api.py、config.py、app.py | 偏好跨重连/重启保留；改口后只使用新偏好；不同设备隔离；清除/遗忘不被旧资料复活 |
| C：交互延迟 | 首段分块、一次性闲置调度、被打断回复记录、原生分轮 | 更快首音频且不中途乱断；连续追问不启动新后台整理；打断后可续讲；长静音不消耗录音上限 |

验收先用临时库和 Fake Provider 做行为验证，再以固定录音和固定回复约束比较在线 P50/P95。真实比较分浏览器/实机、普通问答/工具/视觉、冷启动/预热，不把这些场景混成一个总分位数。

第一版不加入每日扫描、自动权重衰减、自我人格演化、跨设备身份归并。当前目标是“记得准、能纠正、能忘记、读取不拖慢开口”，这些能力可以在现有栈内完成。

## 6. 本次验证结果

全部在临时数据上执行，不读取真实对话正文：

- 首段输入 `可以，我先帮你整理一下，` 没有输出；补到句号后才整段输出。
- `温度是23.5度。` 输出为 `温度是23.` 和 `5度。`。
- 3 条近期消息与 3 条相关消息 ID 完全重叠，一条旧用户偏好最终被注入两次。
- 旧的准确咖啡偏好被 6 条新弱相关记录挤出 5 条检索结果。
- 将原生 auto 录音上限缩至 0.3 秒用于快速验证，纯静音第 6 个 60 ms 包触发 SessionLimitError，heard_speech 仍为 false。正常配置上限为 30 秒；是否收到连续静音包取决于固件，上述验证的是服务端逻辑。
