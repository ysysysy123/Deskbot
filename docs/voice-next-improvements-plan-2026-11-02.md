# Voice 下一阶段改进计划

日期：2026-11-02。依据：用户提供的 Voice Agent 说明及代码审查文本、当前本地 main 源码、11 月 1 日评测记录，以及 [本次分项推送记录](local-improvements-push-log-2026-11-02.md)。

本次完成源码核对与规划，不改运行配置、部署服务或烧录固件。下文耗时为实施粗估，验收数值是拟定目标，均不是新测量结果。

## 1. 当前判断

保留现有模块化语音架构，以实机交互体验为主线：先让修改持续受自动测试保护，再解决工具结果可信度、等待时间和自然打断。现有 MCP、DialogueBackend、长期记忆足以支撑这一阶段。

提供材料中的部分结论需要按最新实现更新：

| 材料中的判断 | 当前核对结果 | 下一步处理 |
| --- | --- | --- |
| 自动监听静音累计到 30 秒可能断线 | 已加入讲话前短缓冲、闲置静音不计时、到时长上限提交；已有离线测试 | 保留修复，补一次实机静音超过 2 分钟的验收 |
| CI 没有运行 Voice 测试 | 根目录 workflow 仍只校验协议 JSON | 第一批补齐 |
| Edge TTS 收齐整段音频才转码 | 当前已将 MP3 流送入 FFmpeg，边接收边输出 PCM；首段短语提前合成也已实现 | 排查现有流式链路的实际等待来源 |
| 缺少普通语音基准 | 已有实际 WebSocket 30 轮串行测试及分段、VAD、记忆规模测试 | 补设备播放和端点指标 |
| 记忆只有消息和摘要 | 已有长期事实、改口、遗忘、来源、闲时整理及上下文预算 | 进入真实表达验收与小幅修正阶段 |
| 实机需要从头增加 AEC | 立创构建配置已有设备端 AEC，板级 codec 声明了播放参考通道 | 验证当前固件与实物参考信号，再补齐打断状态联动 |
| 工具执行前可能播报成功 | 直接动作／拍照路径已先执行再回答；通用模型工具循环仍即时输出文本 | 精确修复通用工具循环 |

## 2. 用现有数据确定优化重点

[11 月 1 日实施与测量记录](voice-memory-implementation-2026-11-01.md)中，固定 2.064 秒合成语音、空历史、单客户端实际 WebSocket 的 30 轮成功回合为：

| 指标 | P50 | P95 |
| --- | ---: | ---: |
| ASR | 93.3 ms | 108.7 ms |
| 本地记忆写入与读取 | 1.4 ms | 1.5 ms |
| 首文字，自 pipeline 启动累计 | 699.2 ms | 4140.9 ms |
| TTS 请求开始至首 PCM，逐轮相减后统计 | 2448.7 ms | 2916.6 ms |
| 服务端首音频发送，自 pipeline 启动累计 | 3471.7 ms | 6919.9 ms |

当前短录音场景优先看 TTS 等待与 LLM 首文字长尾。ASR 约 0.1 秒，先改成流式 ASR 对该场景的收益空间较小；长录音、多人排队时另测。

短首段受控对比中，首音频中位数提前约 450 ms，但多一次 TTS 请求，发送完成中位数慢约 122 ms。因此保留阈值开关，同时观察首声、整轮时长和听感。VAD 默认继续保留 600 ms；既有样本中，450 ms 会把一次 540 ms 的句中停顿切开。

## 3. 第一批：可由 Voice 侧独立完成

### A. Voice CI 与说明同步（P0，约半天）

**修改范围**：根目录 workflow、Voice 测试运行说明、Agent 接口说明。

- 在 PR 和 main push 中运行 Voice Python 测试及浏览器逻辑测试，使用现有 `requirements-test.txt`，准备 Opus 与 FFmpeg 原生依赖。
- 从 `server/voice` 目录运行 pytest，利用现有测试集覆盖单元、HTTP、WebSocket、取消及记忆链路；普通 CI 使用模拟模型。
- 同步 `voice-agent-integration.md` 中已经过时的“Edge 整段转码”“记忆只有摘要”等描述。
- 验收：全新 CI 环境能安装离线依赖并运行现有全部测试；当前基线为 375 项 Python、16 项浏览器逻辑。分支合并保护需另行设置，workflow 本身不会自动禁止合并。

### B. 通用工具循环的结果播报（P1，约 1 天）

**问题范围**：`CameraMcpDialogueBackend.stream()` 的模型工具循环；保留已按真实结果播报的直接动作／摄像头路径。

当前工具流先输出模型文字，等本轮结束后才产出完整 `ToolCall`。因此“见到工具调用再拦截”无法收回已经播出的内容，仅改提示词也不能保证结果顺序。

第一版在允许工具的模型轮次暂存文字，确定工具调用后先执行，成功／失败依据实际结果播报。需要过渡语时由代码输出中性语句，例如“我来查看一下”，不能预先确认成功。没有可用工具的普通问答继续使用现有文本流。

**明确代价**：工具可用但最终没有调用的轮次，也可能等完整模型输出后才开始说话。实施时单独测量这一类问答；若代价明显，再评估小范围意图路由，避免一开始增加额外规划模型。

**验收**：覆盖模型先说成功后返回工具、设备失败、正常成功及用户中途取消这四类实际路径；失败时不播报成功，取消后不执行尚未发出的工具调用。运动接口只确认设备实际回传的状态；收到指令与物理动作完成分别表达。

### C. TTS 与首文字长尾排查（P1，约 1～2 天）

**修改范围**：现有 TTS／转码指标和隔离基准脚本，按测量结果决定具体优化。

1. 在现有阶段计时上补首个压缩音频到达、转码进程就绪等必要时间点，拆清约 2.45 秒中服务响应与转码等待各占多少。
2. 用固定文本与交替顺序比较候选配置；记录首 PCM、首音频、完整输出时长、失败数和请求数。保留既有预热与 P50/P95 统计口径。
3. 检查首文字长尾是否与重试、模型服务响应有关，按日志证据处理。
4. 只有现有 Provider 的主要等待无法消除时，再通过既有 TTS Provider 边界比较替代方案；纳入可用内存、模型加载、声音质量与调用成本。

**验收**：优化前后各有相同场景的 30 轮记录，含失败样本说明和音频试听。拟定首音频 P50 降低至少 20% 为目标，同时报告 P95、整轮时长及失败变化；未达到则保留测量结论，不强行替换默认方案。

## 4. 第二批：接通实机自然打断与端到端测量

### D. 打断控制先于慢任务清理（P1，约 1～2 天）

服务器 `handle_audio()` 当前仅处理 LISTENING 状态，播放期间上行音频不能直接形成新一轮。另一个实际约束是 `abort()` 先等待 pipeline 取消；SenseVoice 的取消需等同步推理线程结束。停音控制与模型清理需要分别评估。

- 明确先令旧回合失效、发出停音控制，再清理旧推理／转码资源的顺序；保留共享模型的并发上限。
- 优先复用现有 `abort`、监听控制和轮次隔离。先验证现有传输顺序是否足以挡住旧回合尾包，再决定是否需要扩展协议字段。
- 用可暂停的模拟 ASR／工具验证：慢任务尚未结束时，停音控制能先完成；旧任务结束后不重新出声，也不混入新指令。

### E. 实机 AEC 与插话闭环（P1，预计 3～5 天，需要固件协作和实机）

**先核对现状**：当前板型、已烧录版本、AEC 运行模式、MIC3 播放参考输入，以及播放时上行音频是否持续。源码已具备 AFE、播放队列清理和播放代次，优先复用。

目标链路：

```text
播放时接收经 AEC 处理的麦克风输入
→ 确认用户开始插话
→ 设备立即停止旧播放并清空旧队列
→ 通知服务端中断旧回合
→ 保留插话开头并提交新指令
→ 正常执行工具或回答
```

Voice 侧负责播放期间输入的处理、取消和新轮次交接；固件侧负责实际采音、AEC、本地停音及队列清理。VAD 状态回调目前主要通知状态变化，还需把有效插话与打断动作接通。

先完成“明确插话可以停止并换题”，再根据实测区分短附和与真正插话。避免把首次实现同时扩大为语义端点模型、声纹识别或完整并行任务系统。

**首轮实机验收场景**：正常音量与较高音量各测播放中明确插话、仅机器人讲话、用户句中停顿；另测连续两轮插话及静音超过 2 分钟后再次说话。记录成功数／总数、误触发、旧音频残留及新指令首字是否完整。明确插话到实际停音 P95 暂以 300 ms 为目标，先取得基线再确定最终门槛。

### F. 设备侧首声与停音计时（随 D／E 一起做）

- 服务端继续记录 ASR、记忆、首文字、首 PCM、首包发送；工具回合单独分组。
- 设备侧在同一单调时钟下记录语音结束判定、收到音频、首次 I2S 输出、播放队列排空，以及插话检测到停音。
- 服务端与设备用会话／轮次关联记录，不直接相减未同步的两端时钟。
- I2S 首次输出作为播放开始的代理；实际“人说完到喇叭出声”“插话到停止出声”用包含人声和喇叭声的同一外部录音时间线验收。
- 采集至少 30 个普通短语音回合；普通问答、视觉工具、动作分别统计。首声同时包含端点等待与设备播放，不能直接与现有服务端首包数字混用。

## 5. 后续候选，由第二批数据决定

| 方向 | 进入条件 | 最小下一步 |
| --- | --- | --- |
| 更自然的轮次检测 | 真实用户的停顿频繁误截或等待明显 | 先比较已有 VAD 参数与最大等待策略，再评估语义端点 |
| 流式 ASR | 长录音或多设备排队使 ASR 成为明显等待来源 | 在 ASR Provider 边界做一个可对比原型，测准确率、延迟和资源 |
| 记忆表达覆盖 | 实际出现“记住／改口／忘掉”漏识别或串用旧信息 | 整理约 20～30 条真实风格的合成表达，测跨重连读回和遗忘，不扩展存储架构 |
| 后台长任务与主动汇报 | 已有明确耗时任务，用户需要中途问进度／取消 | 单任务状态、进度与取消入口，交互与执行分离 |
| 按用户区分记忆 | 确定一台设备有多位长期使用者 | 优先明确切换用户的方式，再决定身份机制 |

端到端语音模型或新的通信／Agent 框架可作为以后独立对照原型。当前优先完成可在现有硬件、协议与 Provider 边界内验收的改动。

## 6. 建议实施顺序与交付

1. **第一批，约 3～4 个有效工作日**：A（CI／说明）→ B（工具结果播报）→ C（TTS／长尾测量与小范围优化）。每项单独提交，更新工作记录。
2. **第二批，约 4～7 个有效工作日**：D（打断控制）→ E（固件与实机闭环），F 的计时随同实现。时间取决于实机、串口与固件协作是否就绪。
3. **第二批验收后**：以实机首声、打断成功率／误触发和工具执行结果决定下一轮投入，选择第 5 节中已有实际需求的方向。

建议下一项先做 **Voice CI 与说明同步**，随后处理 **通用工具结果播报**。两项范围清楚、无需改硬件，可为后面的实时交互修改提供可靠基线。
