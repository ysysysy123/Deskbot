# 语音服务端记忆层接入与延迟评估

评估日期：2026-10-31（America/Los_Angeles）。本次检查当前源码、配置和已有运行日志，没有启动、重启或修改运行服务，也没有调用云端模型。

## 结论

适合借鉴 qq-dsh-bridge 的分层记忆设计，在当前 Python + SQLite 服务中实现。当前已有历史、摘要和相关历史检索；主要增量应是独立的长期事实、事实更新和闲时整理。整套 QQ/OneBot/DSH 桥接不适合作为语音主链路依赖。

历史无工具记录的成功语音回合中，ASR 中位数 131 ms，记忆阶段 6.5 ms，首文字 1.045 秒，首音频 3.950 秒，整轮服务端处理 13.403 秒。首文字到首音频间隔中位数 2.713 秒，值得优先拆分和优化。它包含成句、TTS、转码与发包，不能直接归因为纯 TTS 网络延迟。

这些数值是混合历史版本的日志统计，不能作为当前版本性能承诺。检查时 8000/8003/8004/8006 未监听，尚无本次在线复测。

## 当前服务已有的记忆能力

| 能力 | 当前实现与限制 |
| --- | --- |
| 原始消息 | SQLite 按 Device-Id 保存；当前配置每设备最多 5000 条，超出会删除旧消息，并非永久原文档案 |
| 近期上下文 | 默认最近 10 条；摘要未处理消息可扩大上下文，受 context_limit 约束 |
| 摘要 | 12 条新增消息达到阈值后可整理，约相当于 6 轮完整问答；在回复结束后异步启动，并非真正等待闲置 |
| 历史检索 | 中文二字片段和英文词匹配 SQLite LIKE，最多 5 条；主要按新近排序，没有相关度评分 |
| 用户隔离 | 按设备隔离，重连后延续；同一设备前的不同人目前无法自动区分 |
| 管理 | 已有查询、追加消息和清除 API |

只读数据库计数：553 条消息、16 个设备标识、5 条设备摘要。设备标识数量包含测试数据，不能据此推断真实用户数。

代码依据：[SQLite](../server/voice/src/voice_server/memory/sqlite.py)、[记忆服务](../server/voice/src/voice_server/memory/service.py)、[会话编排](../server/voice/src/voice_server/session.py)。

## 上游哪些设计值得结合

已查看上游 README、memory-store.js、memory-facts.js、memory-search.js 和上下文插件。上游源码为 JavaScript，其事实与检索模块可独立理解，但不是可直接安装到当前 Python 服务的 MemoryProvider。

| 上游机制 | 对本项目的适用方式 |
| --- | --- |
| L0 原文库 | 保留当前 SQLite。若要突破 5000 条历史，再单独决定归档期限；原文保存和模型上下文窗口应分开 |
| L1 会话摘要 | 复用当前摘要表，把整理安排在闲置时，减少连续对话期间的后台模型竞争 |
| L2 长期事实 | 最值得增加：偏好、身份、约定、待办独立存储，记录来源消息与更新时间，按重要性和相关性少量注入 |
| 相关历史检索 | 当前已做中文二字匹配；先增加匹配度排序和原文出处，不必立即引入向量数据库 |
| L3 产物索引 | 当前语音陪伴主流程收益有限，等实际产生文档等产物后再接入 |
| selfNote | 可选保存助手与用户约定的互动风格，例如“用户希望先听完再回答”；与用户事实分开，避免把模型自述当成用户事实 |
| 闲置边界压缩 | 借鉴“对话中优先响应、闲时整理”的原则，不能照搬 30 万 token 阈值或 QQ 消息合批等待 |

建议只增加一张事实表，继续由 MemoryService 封装：device_id、事实类别/键、内容、重要度、来源消息、更新时间、有效状态。事实使用独立于 WebSocket session_id 的设备键，才能跨重连保持记忆。如果以后明确要多人共用设备，再增加用户绑定。

“我喜欢咖啡”改为“我现在不喝咖啡了”时，应更新同类事实的有效状态；上游的完全相同文本去重无法解决这种正常的偏好变更。先处理这一实际需求，再考虑复杂衰减规则。

建议链路：

```text
语音 → ASR → 保存原文 → 读取近期上下文、摘要、少量事实和相关原文
     → LLM 流式回答 → TTS 流式输出
                         ↓ 回复结束且会话空闲后
                    摘要整理、抽取/更新事实
```

闲时任务用一次性计时触发，新一轮到来时顺延；不要新增持续扫描。整理不增加每轮回答前的 LLM 调用。事实注入可先以 10–20 条、500–900 字符作为初始预算，再测真实模型 token 用量和延迟；字符数不能固定换算成 token 数。

现有 summary、recent_messages、relevant_memories 的上下文组装需要扩展 facts；WebSocket 协议、ASR 和 TTS Provider 无需随记忆层调整。若以后要接完整 DSH Agent，可另行实现现有 DialogueBackend，但这不是增加记忆的必要条件。

本次只完成评估及统计工具，尚未实现上述新记忆功能。

## 历史语音回合量化

来源：`/home/yyy/.local/state/deskbot/voice.log`，最后修改时间 2026-10-24 05:18（America/Los_Angeles）。日志没有为每条计时记录提供可直接使用的日期和版本标识，不能可靠按版本拆分。

共解析 175 条回合计时：131 条 success、23 条 cancelled、21 条 error。其中 126 条是成功且有首音频的语音回合，108 条没有工具调用记录，18 条有工具调用记录。另有 2 条成功的文本直入音频回合。success 中其余 3 条没有首音频，不能作为完成语音回复的样本。

以下以 108 条“成功、有音频、ASR > 0、无 tool_calls 记录”的回合作为普通语音的近似样本；未核实每轮请求语义，且混合浏览器与实机路径、不同输入和回复长度。

| 指标 | 中位数 P50 | P95 | 样本数 | 定义 |
| --- | ---: | ---: | ---: | --- |
| ASR | 130.8 ms | 426.7 ms | 108 | 服务端 pipeline 开始至整段识别完成，可能包含 ASR 排队 |
| 记忆阶段 | 6.5 ms | 8.8 ms | 103 | 当前用户消息落库及上下文召回；不包含后台摘要 LLM |
| 首文字 | 1.045 s | 3.524 s | 108 | pipeline 开始至首个非空回复片段，已含 ASR 和记忆 |
| 首音频 | 3.950 s | 6.229 s | 108 | pipeline 开始至首个 Opus 音频包发送完成 |
| 首文字 → 首音频 | 2.713 s | 4.196 s | 108 | 每轮计算差值后取分位数；含成句、TTS、转码与发包 |
| 整轮服务端处理 | 13.403 s | 22.834 s | 108 | pipeline 开始至结束，含回复音频发送、最后写入等 |

有工具调用记录的 18 轮，首音频中位数 4.335 秒，整轮中位数 10.704 秒；回复长度与任务不同，不能据此说工具调用更快。全部 126 条成功语音回合的首音频中位数为 3.977 秒、P95 为 6.161 秒。

21 条历史错误中，19 条处于 TTS 阶段、2 条处于工具阶段。它们包含已记录修复的故障与调试，不能用 131/175 当作当前服务成功率。取消也不等于失败，可能来自主动打断或断开。

P95 采用排序后 `(n-1)*0.95` 位置线性插值。各字段只统计存在该字段的记录；5 条早期样本缺少 memory_ms。没有把错误、取消或无音频的 success 混入成功回复延迟分布。

## “总的语音通话时间”的三个口径

1. **说完到开始听见回答**：当前计时不含此前 VAD 静音等待。配置为 600 ms，因此历史首音频中位数加配置静音窗口约为 **4.55 秒**，还需加设备上传、网络和播放缓冲；这是近似推算，并非设备端测量。
2. **一轮对话从开始说话到结束**：还要加用户讲话时长。若讲话 3 秒，按上述配置和历史整轮中位数推算，约 `3 + 0.6 + 13.403 = 17.0 秒` 才到服务端 pipeline 结束；扬声器播放完成时间还需设备确认。此公式是示例，回复长度改变会直接改变总时长。
3. **一通连续会话能持续多久**：浏览器持续模式没有固定总时长限制，每次录音默认最多 30 秒后提交；既有记录验证过超过 100 秒的持续对话，尚无数小时稳定性结论。

LLM 和 TTS 按句流水执行，阶段存在重叠；不能把各模块的独立总耗时或各项分位数相加来当作端到端时间。现有 tts_ms 包含音频消费与节奏发送，也不能直接作为纯模型合成耗时。

## 单模型历史数据及当前缺项

[已有模型数据](model-benchmark-figures/benchmark-data.json)是独立实验的历史汇总，原始 ASR/TTS 结果目录未找回，本次没有重跑：

- SenseVoiceSmall GPU 中文推理中位数 27.3 ms，五种语言样本中位数约 25.3–34.7 ms；模型加载约 5.99 秒、GPU allocated 峰值约 939 MiB。CPU 批次 RTF 约 0.030–0.031，约表示 5 秒音频推理 150–155 ms，属于按 RTF 推算。
- EdgeTTS 独立实验的首音频中位数约 1.10–1.22 秒。当前服务已增加转码、按句组织和网络路径，不能直接用该值代表实机等待。
- 现有 GLM 单次测试首文本约 847 ms、总生成约 1173 ms；单次样本不代表 P95。
- 本地 NInfer 的 134.42 token/s 来自规则数字序列；普通中文场景记录约 51.3 token/s。当前文件配置为 glm-4-flash，不能将 NInfer 的速度套用到云端语音链路。

当前文件配置还包括 ASR 并发 1、最大连接数 8、Edge TTS；它们是配置上限，不是吞吐实测。当前服务未运行，无法给出其运行时 CPU、内存、显存或当前模型队列长度。

要得到当前版本的可比较结果，下一轮只需固定一批输入和回复约束：普通语音至少 30 轮，工具/视觉另组；保留冷启动一次、预热后统计 P50/P95，并记录输入/输出音频时长。增加“首句就绪、TTS 请求、首 PCM、设备开始播放/播放结束”几个时间点，即可拆清 2.7 秒等待和设备侧延迟。ASR 准确率需要人工转写参考；并发容量需要单独测试，现有日志不足以回答这两项。
